## 2. System Understanding

### 2.1 Problem domain
Condominium / community management system covering property, people, finance, complaints, maintenance, facilities, community comms, visitors, and system audit. RBAC is role-permission based (`users → roles → roles_permissions → permissions`).

### 2.2 Data model — 22 tables + tenancy layer (typos corrected from PDF)

**Tenancy addition (not in PDF)**: A new `tenants` table is added as the root entity. **Every domain table gets a `tenant_id UUID NOT NULL REFERENCES tenants(id)` column**, and PostgreSQL Row-Level Security (RLS) policies enforce tenant isolation at the database layer.

| Domain | Tables |
|---|---|
| **Tenancy (new)** | **`tenants`** |
| Property | `blocks`, `units` |
| People / RBAC | `users`, `roles`, `permissions`, `roles_permissions`, `residents`, `family_members` |
| Finance | `bills` (PDF: `billings`), `payments`, `payment_methods` |
| Complaints | `complaints`, `complaint_categories`, `complaint_updates` (PDF: `complaints_updates`) |
| Maintenance | `maintenance_requests` |
| Facilities | `facilities`, `facility_bookings` |
| Community | `announcements`, `events` |
| Visitors | `visitors`, `visitor_pre_registrations` |
| System | `notifications`, `activity_logs` |

**Typo corrections (do NOT replicate from PDF):**
- `residents.resident_type` → enum `OWNER | TENANT`
- `announcements.tittle` → `title`
- `events.tittle` → `title`
- `events.loacation` → `location`
- `notifications.messaage` → `message`
- Normalize `billings` → `bills` throughout

**Tenant scoping rule**: Every FK relationship scoped within same tenant. Composite uniques: `(tenant_id, ...)`. Example: `UNIQUE (tenant_id, email)` on users.

### 5.4 Database migrations — Flyway, one file per table, tenant-aware
- V1: extensions (uuid-ossp, pgcrypto)
- V2: tenants (root tenancy table)
- V3..V24: domain tables, all with `tenant_id UUID NOT NULL REFERENCES tenants(id) ON DELETE RESTRICT`, indexed
- V25: enable_rls — RLS + `tenant_isolation` policy: `USING (tenant_id = current_setting('app.current_tenant')::uuid)` on every domain table
- V26: seed_roles_permissions (template — copied per tenant on creation)
- V27: seed_dev_data (dev profile only — TWO synthetic tenants for cross-tenant isolation testing)
- V28: refresh_tokens (tenant-scoped)

**RLS is non-negotiable for multi-tenant** — application filtering alone is one bug from a leak.

### 5.5 Authentication & Tenancy — JWT (tenant-scoped) + bcrypt + Spring Security + RLS
- Access token: 15 min, HS256, claims = `userId`, `tenantId`, `roles`, `permissions`
- Refresh token: 7 days, rotating, stored server-side
- bcrypt cost 12
- Endpoints: `POST /auth/login`, `POST /auth/refresh`, `POST /auth/logout`, `GET /auth/me`
- `@PreAuthorize("hasPermission(...)")` method-level

**Tenant resolution flow**:
1. JwtAuthenticationFilter extracts `tenantId` claim from JWT
2. TenantContext (ThreadLocal) set with tenantId
3. Hibernate interceptor sets PG session var: `SET LOCAL app.current_tenant = '<uuid>'`
4. RLS policies enforce isolation (even raw SQL cannot leak)
5. TenantContext cleared in `finally`

**Tenant resolution strategy (decided)**: `X-Tenant-Slug` header in dev, `condoA.mycomunity.app` subdomain in prod. `TenantResolver` interface with two implementations behind Spring profile.

**Tenant onboarding**: `POST /admin/tenants` (super-admin only) creates tenant + copies role/permission templates + seeds initial tenant Admin.

### 5.6 Frontend architecture
- Routing: React Router v6
- Data: TanStack Query + Zustand
- Forms: React Hook Form + Zod
- HTTP: Axios with JWT refresh interceptor
- UI: Tailwind + Headless UI
- API client: auto-generated from backend OpenAPI via `openapi-typescript`

### 5.7 Testing strategy
| Layer | Tool | Target |
|---|---|---|
| Backend unit | JUnit 5 + Mockito | ≥70% lines |
| Backend integration | Spring Boot Test + Testcontainers (Postgres) | All repos + controllers |
| Backend contract | Spring REST Docs → OpenAPI | All endpoints |
| Frontend unit | Vitest + RTL | ≥60% lines |
| Frontend E2E | Playwright (post-MVP) | Critical flows |
| Security | OWASP Dependency-Check + npm audit | Zero high/critical |

**TDD discipline**: Every feature starts with a failing test. Prefer vertical slices (API → service → repo → DB) tested end-to-end with Testcontainers.

## 6. Final Architecture

### 6.1 Runtime view (dev)
```
┌─────────────┐       ┌──────────────────┐      ┌────────────────┐
│  Browser    │──────▶│  React (Vite)    │─────▶│ Spring Boot    │
│             │       │  localhost:5173  │      │ localhost:8080 │
└─────────────┘       └──────────────────┘      └───────┬────────┘
                                                        │
                                                        ▼
                                              ┌───────────────────┐
                                              │ PostgreSQL 16     │
                                              │ docker-compose    │
                                              │ localhost:5432    │
                                              └───────────────────┘
```

### 6.2 Request flow (create complaint)
```
User → React form → Axios POST /api/complaints (JWT)
     → Spring Security filter (validate JWT, load user+perms)
     → TenantContext set from JWT claim
     → SET LOCAL app.current_tenant = '<uuid>'
     → ComplaintController (@PreAuthorize("hasPermission('COMPLAINT_CREATE')"))
     → ComplaintService (business rules)
     → ComplaintRepository (JPA, RLS-scoped)
     → PostgreSQL insert
     → ActivityLogService (async audit)
     → NotificationService (notify Manager role)
     → Response DTO → React TanStack Query cache update
```

### 6.3 Module responsibilities
- `security` owns auth; no other module imports JWT internals
- `tenancy` owns TenantContext, resolution filter, tenant CRUD, super-admin endpoints
- `common` owns `TenantAwareBaseEntity` (id, tenantId, createdAt, updatedAt, createdBy, updatedBy)
- Domain modules expose services via interfaces; cross-module calls through interfaces, never repositories
- **Every domain entity extends TenantAwareBaseEntity** — enforced by ArchUnit test in CI

### 6.4 Integration points
| Integration | Protocol | Notes |
|---|---|---|
| Frontend ↔ Backend | REST/JSON over HTTPS (prod) | OpenAPI 3 contract |
| Backend ↔ PostgreSQL | JDBC | HikariCP pool |
| Backend ↔ Email (future) | SMTP | Profile-gated; mock in dev |
| Backend ↔ SMS (future) | Twilio or local | Profile-gated |
| Backend ↔ File storage | Local FS (dev) → S3 (prod) | StorageService interface |

## 7. SDLC + CI/CD Plan

### 7.1 Development workflow
```
Story → Brainstorm doc (docs/specs/) → Plan doc (docs/plans/) →
  Feature branch → Failing test → Implementation → Green test →
  Code-reviewer agent → 8-actor validation →
  Draft commit message → USER REVIEWS & EDITS → Commit → PR → CI green → Merge
```

### 7.1.1 Commit Workflow (per user instruction — overrides default auto-commit)
**Mandatory for every commit, no exceptions:**
1. Stage files (specific paths, never `git add -A`)
2. Draft commit message → present to user (do NOT run `git commit` yet)
3. User reviews, edits, hands final message back
4. Run `git commit -m "<final message>"`
5. **No `git push` ever** unless user explicitly says "push"
6. Applies to first commit and every subsequent commit

This supersedes SOP Section 13.3 — no auto-commits, period.

### 7.2 Branching model
- `main` → protected, production-ready
- `dev` → integration branch
- `feature/<slice>` → short-lived, merged via PR
- No direct pushes to `main` or `dev`

### 7.3 CI pipeline — GitHub Actions
**`ci-backend.yml`** (trigger: `backend/**`, `pom.xml`)
1. Checkout
2. Setup JDK 17 (Corretto)
3. Cache `~/.m2`
4. `mvn verify` (unit + integration via Testcontainers)
5. OWASP Dependency-Check
6. Upload JaCoCo coverage
7. Fail if coverage < 70% on changed files

**`ci-frontend.yml`** (trigger: `frontend/**`)
1. Checkout
2. Setup Node 18
3. Cache `node_modules`
4. `npm ci`
5. `npm run lint`
6. `npm run typecheck`
7. `npm run test`
8. `npm run build`
9. `npm audit --audit-level=high`

### 7.4 CD pipeline (stubbed now, activated at MVP)
- Stage 1 — Dev: merge to `dev` → build images → push GHCR → deploy dev env
- Stage 2 — Staging: manual approval → deploy staging → smoke tests
- Stage 3 — Prod: manual approval + checklist → blue/green

### 7.5 Rollback strategy
- DB: no Flyway undo; forward-fix migrations + backups before deploy
- App: previous Docker image tag retained; rollback = re-deploy previous tag
- Trigger: smoke fail, error rate > baseline, or manual
